# MCAP real Firebase browser acceptance

This suite runs the actual static OMAX application and its Firebase **8.10.1** SDK against disposable Auth, Firestore and Storage emulators. All data, accounts, tokens and object contents are synthetic. It requires no production login, exported business data, Firebase rule publication or F12 action.

## Run

Use Node 22, Java 21 and an isolated dependency directory. For example, in PowerShell from this worktree:

```powershell
$mcapTools = Join-Path $env:TEMP 'omax-mcap-browser-tools'
npm install --prefix $mcapTools --no-save --no-audit --no-fund firebase-tools@15.32.1 firebase@8.10.1 playwright@1.56.1
$env:NODE_PATH = Join-Path $mcapTools 'node_modules'
& (Join-Path $mcapTools 'node_modules/.bin/playwright.cmd') install chromium
node scripts/mcap-emulator-browser.cjs
```

On Linux, use the same packages and expose the dependency directory through `NODE_PATH`; provision Chromium using that directory's `node_modules/.bin/playwright install chromium`. The dedicated `real-firebase-browser` job in `.github/workflows/mcap-storage-test.yml` runs the full procedure automatically. Windows tests use installed headless Edge; Linux CI uses Chromium.

The runner starts only `demo-mcap-browser` on loopback: Auth `9097`, Firestore `8188`, Storage `9197`, hub `4447`, logging `4597`. Firebase also opens its Firestore UI websocket port `9150`. The suite refuses to run directly unless the runner supplied the exact emulator environment. The Firebase CLI shuts the services down after the test exits. Logs are `firebase-debug.log`, `firestore-debug.log` and, when provided by the CLI, `storage-debug.log`; CI retains them on failure.

For a focused local diagnosis, set `MCAP_EMULATOR_ONLY` to `native calendar`, `lost real commit`, `history import`, `archive`, `actor change`, `corrupt field`, `in-flight`, `cutting file`, `specialized`, `job workbook`, or `job restore`. This still creates a fresh full authority and runs ordinary-save acceptance before the selected cases. Clear the variable for full acceptance. The filter is rejected in CI, and a filtered run is never evidence that the whole suite passed.

## Test-only configuration boundaries

The real SDK browser bundles come from the installed Firebase package and are served locally. Requests are allowed only to the test HTTP server and those three emulator origins. Normal Firebase operations use native emulator requests. Explicit fault cases below intercept individual real responses to drop a committed acknowledgement, hold a staging response during sign-out, or tamper with field-download bytes; they do not supply synthetic authority or replace a service.

`tests/fixtures/mcap-emulator-identity.cjs` rebinds the source's pinned production project, bucket and allowed UID to a demo project, demo bucket and synthetic owner in the **served copy** of JavaScript and the **temporary copy** of the rules. All role, revision, metadata, checksum, immutable-object and deny rules remain intact. The served `core.js` copy enables the source write switch. The served `omaxShardedReadback.js` copy permits downloads only from the exact loopback Storage origin because emulator download URLs use HTTP. The checked-in application keeps its production identity checks, HTTPS requirement and `MCAP_SHARDED_WRITES_ACTIVE = false`.

Only fixture preparation uses local emulator administrative REST endpoints: seed the synthetic member and historical state, adjust synthetic membership for a denial test, and remove a test manifest for corruption recovery. Ordinary saves, index creation, stale-writer attempts, subscriptions, Storage uploads/downloads and rule-denial assertions use the actual browser SDK. No rule-disabled context is used for those operations.

The cutting-file cases also administratively seed one valid synthetic object attributed to a different creator, to verify that an active owner can read it but cannot delete it. A barrier on the native metadata Write-channel request changes synthetic membership to viewer before the real emulator evaluates the batch. Membership remains denied until the application receives the real failure and starts compensation; a barrier on that exact Storage delete restores owner before forwarding it. Native Storage compensation therefore runs under the restored writer role. The fixture neither synthesizes permission errors nor disables rules for the tested operations.

The active test authority includes an opaque segmented extension that makes the logical state larger than 975,000 bytes. Its historical legacy document stays smaller and is checked exactly after active saves and rejected old-client writes. This fixture provisioning is not a test or invocation of the production operator activation tool.

## Acceptance scope

The suite checks ordinary saves, exact full-state refresh, two-session realtime convergence, specialized water/pump/material/cutting-job operations, native calendar scheduling/completion, stale-client rejection, Storage-rule denials, membership denial, a dropped response after a real committed index write, and missing-manifest recovery. Exact business preservation and revision/readback checks remain required even when the UI has already displayed an optimistic result.

Historical import cases feed reviewed rows to the production purchase, pump-hours, RPM and maintenance import API. They capture the mandatory native download and parse it independently to verify exact pre-import state, including the oversized opaque field. They check source provenance, purchase allocations without inventory replay, idempotent reruns and changed-preview denial. Workbook parsing/file-selection UI is not claimed by these API tests.

The initial synthetic authority includes a linked maintenance task and inventory item with retained completion/note evidence. Task and stock archive/restore cases verify exact payload transfers, unchanged unrelated fields, history and financial-report stability before and after full reload, confirmation binding and peer-browser convergence. These are record restoration tests, not a whole-database backup restore. During actual committed-response-loss Recovery Mode, the native cloud-export button must download the independently verified current Storage authority rather than the retained older local baseline or legacy Firestore document.

The account-change case holds an actual new-manifest download during staging, signs out through the native Auth SDK, then releases the response. It requires failure, zero outbound authority-index writes, unchanged verified state in the other browser and exact reload after signing back in. The specialized API need not expose a `stateWriteAttempted` flag on every definite failure; observed native requests and independent authority comparisons supply the no-write evidence.

Corrupt-download cases change one byte in an actual segmented opaque-field response while preserving its length. At startup this must prevent adoption and writes, leave the index and legacy document unchanged, and keep the failed-load listener stopped. After a genuinely committed index transaction it must instead enter Recovery Mode, preserve the older loaded baseline and block retries. Removing the injected transport fault and explicitly reloading must independently recover exactly one committed record. These cases prove checksum rejection and recovery for corrupted downloads, not physical mutation of a stored emulator object or production incident handling. Fault routes fall through to the original exact-origin network allowlist.

The in-flight race uses the native pump-log form in both browsers, with both realtime listeners active. The contender stages its immutable state and reaches a real authority-index commit request, which the test holds before sending. The other browser then submits and verifies its own native form. Releasing the contender must produce an actual emulator rejection, leave the winning index/state exact, retain the rejected form's date/time/RPM and show a failure instead of success. Conservative uncertain outcomes must disable retry and retain the prior loaded baseline. After both browsers reload the winner, a fresh native resubmission can add the reviewed second record without losing the first. Every unrelated field, old pump row and legacy document is compared exactly. The barrier controls request ordering; it does not synthesize a CAS response or unsubscribe either listener.

`tests/fixtures/mcap-cutting-files.cjs` runs the production attachment upload/list/open API for DXF, ORD and OMX using owner/admin/operator roles. It verifies canonical MIME, metadata persistence across reload, DXF preview availability, verified-byte fallback opening, independent SHA-256 and byte equality, and unchanged complete business authority/index/legacy state. Raw native requests must reject object overwrite, metadata updates, listing, compatibility/file-document updates and deletes, and sixteen malformed object variants including zero-byte and 50 MiB + 1-byte bodies. Viewer reads remain allowed while direct writes/deletion and application uploads are rejected; inactive or malformed memberships, another UID and anonymous reads are denied. A different creator's otherwise valid object is readable but not client-deletable by owner.

The definite-metadata-denial case uploads a real object, receives an actual Firestore permission denial, and requires exactly one native compensation delete with verified absence and no new file document. A fresh successful retry must retain previous file identities, use a new object path, persist across reload and leave the full active state and index exact. The existing attachment-service regression script and creator-only/15-minute cleanup-contract script also run in the Node CI job. The browser does not simulate passage of the 15-minute expiry interval or claim native file-selection UI coverage.

The initial attachment job is built with the production pure business planner and category validator before synthetic authority provisioning. It avoids making attachment acceptance depend on another live create. The separate specialized cutting-job case creates through the real application API and holds the final post-commit manifest download for four seconds without changing its bytes. Storage chronology verification has a fixed 60-second per-read deadline for full immutable reconstruction; legacy Firestore keeps its three-second deadline. Exact committed-state comparisons, captured-target checks, bounded stale reads, no write replay and no late adoption remain required. Deterministic clock regressions cover both deadlines, late completion and changed data at the committed revision.

`tests/fixtures/mcap-job-import-ui.cjs` builds a valid synthetic XLSX ZIP in memory, with a decoy summary sheet and the actual Cutting Jobs sheet. Native file input, preview, review checkbox, confirmation and trusted backup-download click are exercised. Cancelling must create neither a backup nor a write. Confirming must download exact complete pre-import authority plus the separate local material-setting receipt, append one active and one completed job with original worksheet-row provenance, reuse the reviewed project/category identity, retain old jobs/unrelated fields and survive reload/peer convergence. A repeated workbook is classified as duplicate with no ready rows or second write/download. The workbook uses canonical project/category naming; a reviewed rename retains the existing folder ID.

The native Deleted History button is tested after an exact job-to-trash save. A viewer-role denial must report failure, keep the exact archive and roll back only the owned restoration. Owner retry must independently verify the original ID/payload, retain history/attachments and survive full reload and peer convergence. Job restoration now uses the existing guarded restore proof/CAS/readback instead of the generic local ID-regenerating path and deferred save. The renderer waits for verification and disables the button while pending. Native archive selection is bound to its exact clicked payload; non-first archive positions, unchanged other trash, numeric IDs, expiry/collisions, lost acknowledgements and the canonical-chronology review blocker have Node regressions. Completed-job restore shares this guarded path and is covered by the Node suite; the native browser restore case selects an active job. This is record restoration, not whole-database backup restoration.

Passing emulator acceptance does not establish production IAM, deployed-rule identity, current source/candidate equality, production CORS, independent latest backups or operator approval. Those remaining release gates are tracked in `MCAP-CUTOVER-ACCEPTANCE.md`.
